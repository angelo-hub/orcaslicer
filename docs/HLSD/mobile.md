# Mobile build of the slicing core

OrcaSlicer's slicing engine, `libslic3r`, has no dependency on wxWidgets or OpenGL. The mobile build packages that engine, plus a thin C++ façade, as a static library that a React Native app links through Nitro Modules. The desktop GUI is not part of it.

## What the build produces

`ORCA_MOBILE=ON` on the root CMake project builds:

- `libslic3r` and the in-tree libraries it links (`deps_src/`), unchanged.
- `libslic3r_mobile` (`src/mobile/core/`), the façade. It is the only public surface of the mobile library: plain C++17, no platform or toolkit includes, so the same code serves iOS and Android. `Session` is one project: the preset bundle, the model and the print, with synchronous slicing that the bridge runs on its own worker thread and a `cancel()` that is safe from any thread. Loading presets installs every vendor present in the resources directory's `profiles` into the data directory's `system` folder, where the preset bundle reads them, as the desktop's updater does for the vendors the user enabled; the app fetches only the vendors the user chose. Option metadata comes out as JSON so the app can generate its parameter editor from `PrintConfigDef` instead of hand-writing forms.

It does not build the GUI library, the CLI executable, the embedded Python runtime, the developer tools or sandboxes. The in-tree libraries that only the GUI uses (`hidapi`, `imguizmo`, the `hints` tool) are skipped as well. Everything else in the root project is left as it is; when the option is off the desktop builds are unaffected. `BUILD_TESTS` still works on a desktop host and adds the `tests/mobile` suite, which slices a real model through the façade against the shipped vendor profiles.

`scripts/build_ios_core.sh` drives the two-stage build for iOS and merges the static archives of one or more slices (device, simulator) into `OrcaCore.xcframework`, whose headers are the façade's headers only. `scripts/build_android_core.sh` does the same for one Android ABI with the NDK: the archives are merged with `llvm-ar` into `build/android-core/<abi>/libOrcaCore.a`, with the façade's headers next to it, which the Nitro module's Android build imports.

## Dependencies

The dependency superbuild in `deps/` gains a platform file per mobile OS. `deps-ios.cmake`, selected when `CMAKE_SYSTEM_NAME` is `iOS`, forwards the iOS description (system name, sysroot, architecture, deployment target) to every CMake-based dependency, since ExternalProject does not forward it, and sets the flags the autotools and OpenSSL recipes need. `deps-android.cmake`, selected when the NDK's toolchain file has set `ANDROID`, forwards the ABI, platform level and STL the same way, hands the autotools and OpenSSL recipes the NDK's per-API clang wrappers and LLVM binutils (the `<triple>-ar` names autoconf derives from `--host` do not exist in the NDK), and keeps OpenCV in the unix prefix layout instead of its Android SDK layout. On both systems zlib comes from the SDK or NDK rather than the prefix. `DEPS_MOBILE`, forced on for iOS and Android and available on any host, selects a dependency list that leaves out what the core does not link: wxWidgets, GLEW, GLFW, OpenCSG, libcurl, FFmpeg, Python and wxInspector. A desktop host builds that list to compile the core and run the façade tests natively. `DEPS_MOBILE_PLUGINS` adds Python back for the plugin runtime: on iOS as BeeWare's prebuilt `Python.xcframework` (`deps/python3/python3-ios.cmake`, nothing compiled), on a host through the desktop recipe.

Two constraints shape the recipes:

- CMake's built-in iOS and Android support restricts `find_package` to the SDK or NDK sysroot. The deps prefix is added as a find root with mode `BOTH` so dependencies and the core still find each other, while `CMAKE_IGNORE_PREFIX_PATH` keeps host package managers out.
- Nothing built for iOS or Android can execute on the build host, so no recipe may run a program it just compiled. The autotools recipes are configured with an explicit `--host` for the same reason.

## Layering above the core

`mobile/packages/orca-core` is the Nitro Module. Its TypeScript spec (`src/specs/OrcaCore.nitro.ts`) mirrors `Session.hpp` one to one, and nitrogen generates the C++ spec classes that `cpp/HybridOrcaSession.cpp` implements over the façade. The façade is not thread-safe, so the bridge serializes every call with one mutex per session: promise-returning methods (load presets, import, arrange, slice, export) run on Nitro's thread pool holding it, synchronous methods take it with `try_lock` and throw while a long operation holds it, and `cancel()` never takes it. Progress callbacks are void-returning JS functions, which Nitro dispatches to the JS thread, so the slice thread may call them directly.

Memory is the constraint that shapes the slice path. A phone has a few gigabytes and iOS does not fail `malloc`: the kernel kills the process once it crosses its per-process limit, so nothing inside `libslic3r` can catch an exhaustion. The bridge therefore turns an imminent kill into a cancellation. For the lifetime of one `slice()` it runs a watchdog that polls `os_proc_available_memory()` (the headroom left before that limit) and subscribes to the kernel's critical memory-pressure event; either signal calls `Session::cancel_out_of_memory()`, which is the thread-safe `cancel()` plus a reason, and the slice returns `SliceOutcome::OutOfMemory` with the half-built print freed, so the app can offer to simplify or shrink the model instead of reporting a crash. The façade keeps the figure in the platform layer because it has no platform includes; it only exposes the cancel and the outcome. Two measures lower how often the watchdog trips: `slice()` frees the plate's previous G-code result before building the new one, so old and new toolpaths never coexist at peak, and the bridge caps TBB's worker count from the device's physical memory (`Session::set_thread_limit`, roughly one worker per 1.5 GB), since every worker holds its own layer intermediates and the desktop's every-core default assumes tens of gigabytes. The one-tap recovery after such a cancel is `Session::simplify_object`, the desktop Simplify gizmo's quadric edge collapse run over the object's parts; `Session::repair_object` re-runs the STL-import repair for meshes that slice badly rather than slowly.

The Expo app (`mobile/apps/orca`) owns everything that is not slicing: file import, sending G-code, and fetching vendor profiles from the repository into the core's resources directory.

The façade owns all access to `Print`, `Model` and the preset bundle. The renderer (`OrcaViewportRenderer` in the Nitro package's `ios/` directory, Objective-C++ over Metal, shader compiled at runtime) never includes `libslic3r`; it reads the façade through `Session::mesh()` (an object's triangles in world space with per-face normals) and `Session::preview()` (the exported toolpath as one vertex per G-code move with libvgcode's segment convention, plus layer heights and tool colours). Geometry therefore never crosses the JavaScript boundary: the app holds handles and sends commands. The `OrcaViewport` Nitro View (Swift) receives a session id as a prop and finds the session in `SessionRegistry`, which hands out the façade under the session's mutex with `try_lock`, so a redraw during a slice keeps the last frame instead of blocking. Mode, layer range and a revision counter are props; the camera is native (orbit, two-finger pan, pinch, double-tap to fit).

## Preset files and cloud sync

User presets reach the phone two ways, both owned by the façade so the on-disk result matches the desktop's.

`Session::import_presets` wraps `PresetBundle::import_presets` for the desktop's exports: a single preset `.json`, a `.zip` of presets, or an `.orca_printer` / `.orca_filament` / `.orca_bundle` archive. The bundle classifies each file by its `*_settings_id` key, resolves `inherits` against the installed vendor profiles and saves the difference from the parent with its `.info` sidecar, exactly as desktop import does. One deviation: archives that carry `bundle_structure.json` would normally become a read-only `_local/<bundle id>` bundle, which cannot be edited, deleted or synced; the façade passes `ignore_bundle_structure` so they land as ordinary user presets instead. The result names what was imported, what clashed with an existing user preset (the app asks once, then calls again with overwrite on) and what was skipped, with the reason and, for a missing parent, the vendor that ships it when that vendor is present in resources. The app turns a missing parent into a download of that printer's profiles and a second attempt. `Session::export_presets` (`PresetArchive.cpp`) writes the same layouts the desktop's Export Preset Bundle dialog does, including the flattened printer copy with its print-host fields stripped, so a bundle made on the phone imports on the desktop with File > Import > Import Configs.

Orca Cloud sync splits along the same line. The façade does the preset side with the desktop's own functions: `cloud_push_payload` is `get_differed_values_to_update` (the difference from the parent plus name, type, version and inherits), `cloud_apply_pull` is `load_user_presets` over a full pull (a preset missing from the pull that was synced before is removed locally, so partial pulls are never applied), `cloud_mark_synced` is `set_sync_info_and_save`, and deletions keep their `.info` sidecar with `sync_info = delete` until the server confirms. `set_cloud_user` picks the user preset folder, `data/user/<user id>` or `data/user/default` when signed out, before presets load. The app (`lib/cloud/`) owns HTTP and policy: Supabase sign-in by password or through the desktop's hosted sign-in page with PKCE, tokens in the Keychain, the `setting_id` as the same UUIDv5 the desktop derives from user id and preset name, one sync run as delete, pull, push with the desktop's conflict handling, triggered on foreground, after a preset is saved or deleted, or by hand. Nothing runs on a timer.

## Python plugins

The desktop's plugin host (`src/slic3r/plugin`) runs inside the mobile core when it is built with `ORCA_MOBILE_PLUGINS` (`scripts/build_ios_core.sh -p`). The app keeps the feature behind its own flag (`EXPO_PUBLIC_ORCA_PLUGINS`, or the developer switch on About), and a core built without the runtime answers every plugin call with "not supported" through `src/mobile/core/plugin/PluginsStub.cpp`, so the bridge has one shape either way.

**What is shared and what is replaced.** The plugin files compile unchanged except where they needed wx: `PluginManager`, `PluginAuditManager`, `PluginConfig` and `PythonInterpreter` expose seams the application fills in — a main-thread dispatcher for lifecycle callbacks, a permission prompt, the preset bundle that carries per-preset plugin config, and a Python home override. `GUI_App::init_plugin_gui_wiring` fills them with wx on the desktop; `src/mobile/core/plugin/Plugins.cpp` fills them headlessly. Three desktop files are replaced outright: the cloud service becomes a null one (the app owns the catalog, see below), `orca.host.app` loses the Plater, and `orca.host.ui` keeps the desktop's names and signatures over an event channel instead of dialogs. The page host is the app itself: a pages capability's HTML opens in a React Native web view with the same `window.orca` bridge the desktop's plugin tabs inject (`lib/plugins/pageBridge.ts`, kept in sync with `PluginPages.cpp`), the page's `postMessage` reaches the plugin's `on_message` through `Plugins::page_send`, and the plugin's `post_message` comes back as a `page-message` event while the screen holds the capability's message sender. The slicing-pipeline capability runs where it does on the desktop: the geometry steps through the `Print` hook `PluginManager::initialize` installs, and the G-code step from `Session::export_gcode` on the exported file in place (`core/plugin/PluginPipeline.cpp`, the same dispatch as `GUI/PostProcessor.cpp`). `Session::slice` refreshes the config's `plugins` manifest before `Print::apply`, as the desktop's backend does. `PluginResolver`'s job — telling the user a preset names a plugin the host cannot resolve — is `Plugins::check_preset_refs`, which the app consults before a slice; the hooks themselves skip an unresolved reference.

**The runtime.** CPython 3.14 from BeeWare's Python-Apple-support: a dynamic `Python.framework` per slice that the orca-core podspec vendors, and a standard library the app's `with-python-runtime` config plugin copies into the bundle under `python/lib/python3.14`, turning each extension module into a one-binary framework as iOS requires (BeeWare's `build/utils.sh`). `PythonInterpreter` is pointed at that directory, runs with signal handlers off, and writes `.pyc` files under the data directory since the bundle is read-only. One interpreter serves the process and is never finalized. The desktop embeds 3.12; plugins declare `requires-python >= 3.12`, so the newer runtime runs the same packages, but nothing can run `uv`, so a plugin whose declared packages are missing fails to load with a message saying so.

**Threads and answers.** Every Nitro call that can enter Python is a Promise on Nitro's pool, never a synchronous call on the JS thread, because a plugin may block waiting for the app: a permission request or an `orca.host.ui.message()` becomes a `PluginEvent` with a request id, the app shows an alert, and `pluginAnswer` releases the plugin (a deny after a timeout otherwise). Process creation is denied without asking. Lifecycle callbacks run inline on the worker that finished a load, since there is no UI thread they must reach.

**The catalog and the files.** The app talks to Orca Cloud's plugin endpoints itself (`lib/plugins/api.ts`) and writes a plugin into the directory layout the desktop uses — `orca_plugins/_subscribed/<user id>/<uuid>/` with the entry file and a `.install_state.json` in the desktop writer's key order — so the shared `PluginManager` discovers it as a cloud install, and a directory the desktop wrote reads the same way. Download requests send `os=macosx`, since the service has no iOS value and packages are pure Python; the service's `returned_os` goes to a mobile-only `cloud_meta.json`, never into the sidecar the desktop rewrites.
